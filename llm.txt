0. HOW TO USE THIS DOCUMENT
================================================================================

0.1 Reading order

  - Implementing from scratch: read 1–4 for context, then 5–8 in order (they
    build on each other), then 9 (the API) and 11 (the worker). 12–14 are
    reference for details 9 and 11 point at. 15–18 are cross-cutting
    requirements that apply to every section.
  - Reviewing an implementation: use 9, 11 and 15 as checklists. Every
    endpoint in 9 has a "Tests" block; every one of those tests should exist.
  - Answering "why is it like this": see the Decision log (20) and the
    "Reasoning" notes inside each section.

0.2 Normative language

  MUST / MUST NOT   — required; the implementation is wrong without it.
  SHOULD            — strongly recommended; deviate only with a recorded reason.
  MAY               — optional.
  PRESERVE          — this behaviour exists in the Next.js backend today and
                      the frontend depends on it; keep it byte-compatible.

0.3 Fixed facts about the environment

  - The Rust engine (`truent` binary) is finished and is NOT being rewritten.
    The Python backend shells out to it.
  - The Next.js app in `web/` stays as the frontend. Its API route handlers
    (`web/app/api/**`) and its worker (`web/scripts/scan-worker.mjs`) are what
    the Python backend replaces.
  - PostgreSQL stays. The existing tables (created by Prisma migrations under
    `web/prisma/migrations/`) are reused as-is so that no data migration is
    required.
  - Stripe stays as the card-billing provider.
  - Civic Auth stays as the OAuth/passkey/embedded-wallet provider.

0.4 Conventions used in this document

  - Paths are relative to the repository root unless they start with `/`.
  - JSON examples use real field names. Values marked `<…>` are placeholders.
  - "Engine" always means the `truent` binary. "Backend" always means the
    Python service described here. "Frontend" means the Next.js app.
  - Timestamps are UTC, ISO-8601 with milliseconds, `Z` suffix, e.g.
    `2026-09-24T16:36:42.444Z` — this is what the frontend parses today.
  - Money is integer minor units (cents). `49900` = $499.00.

================================================================================
1. WHAT IS BEING BUILT
================================================================================

1.1 One-paragraph summary

  A Python service with two processes — an HTTP API and a scan worker — that
  together replace the server-side half of the Truent web dashboard. The API
  signs users in (email/password, Web3 wallet signature, Civic), accepts
  source-code submissions, enforces per-user quotas, queues scans, serves scan
  history and reports, lets users triage findings, and provisions paid plans
  through Stripe. The worker claims queued scans from PostgreSQL, runs the
  `truent` binary on the submitted source, maps the engine's JSON output into
  durable findings, and deletes the submitted source when done.

1.2 In scope

  - HTTP API (FastAPI) exposing the routes in section 9.
  - Scan worker (section 11), runnable as one or many replicas.
  - Session issuance and verification (section 8).
  - Stripe checkout + webhook provisioning (section 13).
  - A catalog endpoint that exposes engine metadata (taxonomy, pathways,
    attack chains) so the frontend can stop shipping `lib/catalog.json`
    (section 14). This is additive; the frontend may keep its JSON file.
  - Health endpoints, structured logging, metrics hooks (section 16).
  - Alembic-managed migrations that start from the current Prisma schema
    (section 7.6).
  - Tests at unit, integration and engine-contract level (section 18).

1.3 Out of scope (explicit non-goals)

  - Rewriting or wrapping any detector logic in Python. The engine is the
    only source of findings.
  - Serving HTML. The frontend renders pages; the backend returns JSON only.
  - GitHub repository scanning (a `sourceType` of `repo`). The schema has the
    columns (`sourceType`, `sourceRef`) but the current backend disables it
    until a GitHub App flow exists. Keep it disabled; reject `sourceType`
    other than `code`.
  - Crypto (on-chain) payments provisioning subscriptions. The existing route
    is deliberately fail-closed and MUST stay that way (section 13.4).
  - Multi-tenancy beyond "one user owns their scans". No teams/orgs.
  - Running the engine's live `probe` or `symbolic` commands on behalf of
    users. The dashboard runs static engines only (`scan`).

1.4 Success criteria

  - The existing frontend works unchanged against the Python backend except
    for the authentication client changes listed in section 19.3 (NextAuth is
    removed from the frontend; the rest of the pages are untouched).
  - `web/tests/scan-worker-core.test.mjs` has a Python twin that passes with
    identical expectations (section 18.2).
  - A scan of `examples/evm_token.sol` submitted as `solidity` produces exactly
    one finding, `evm_single_eoa_admin`, severity `high`, evidence `lead`,
    exploitability `unlikely`, line 27 (section 18.4).
  - No submitted source survives in the database after a scan reaches
    `complete` or terminal `failed`.
  - No secret, session token, cookie value or submitted source ever appears
    in a log line.

2. SYSTEM OVERVIEW
================================================================================

2.1 Components

  ┌────────────────────┐   HTTPS (same origin via reverse proxy)   ┌──────────────────────┐
  │  Next.js frontend  │ ────────────────────────────────────────▶ │  Python API (FastAPI) │
  │  web/ (pages only) │ ◀──────────────────────────────────────── │  uvicorn, N replicas  │
  └────────────────────┘        JSON + session cookie              └──────────┬───────────┘
                                                                              │ SQL (asyncpg)
                                                                   ┌──────────▼───────────┐
                                                                   │      PostgreSQL       │
                                                                   │  User, Scan, Finding, │
                                                                   │  Subscription, …      │
                                                                   └──────────▲───────────┘
                                                                              │ SQL (claim/update)
                                                                   ┌──────────┴───────────┐
                                                                   │  Python worker(s)     │
                                                                   │  claims Scan rows,    │
                                                                   │  runs `truent scan`   │
                                                                   └──────────┬───────────┘
                                                                              │ subprocess (argv, no shell)
                                                                   ┌──────────▼───────────┐
                                                                   │  truent binary (Rust) │
                                                                   │  --output json        │
                                                                   └──────────────────────┘

  External services: Stripe (checkout + webhooks), Civic Auth
  (`https://auth.civic.com`, OIDC), an Ethereum JSON-RPC endpoint (only for
  the fail-closed crypto verification route).

2.2 Processes

  api      `uvicorn truent_backend.main:app` — stateless; any number of replicas.
  worker   `python -m truent_backend.worker` — stateless apart from the temp
           directory it creates per scan; any number of replicas; claims work
           with `FOR UPDATE SKIP LOCKED` so replicas never collide.
  migrate  `alembic upgrade head` — run once before a release, never at
           process start.

2.3 Request path for a scan (happy path)

  1. Browser POSTs `/api/analyze` with `{code, language, projectName}` and the
     session cookie.
  2. API verifies session → loads user + subscription → checks per-minute and
     monthly quotas → validates body → INSERTs a `Scan` row with
     `status='queued'` and `sourceContent=<code>` → returns 202 with
     `{scanId, status:"queued", createdAt}` and `Location: /api/scans/<id>`.
  3. Browser polls `GET /api/scans/<id>` every 2 s (existing frontend
     behaviour, up to 150 attempts).
  4. Worker claims the row (`queued` → `processing`, `attempts+1`,
     `claimedAt=now`, `workerId=<id>`), writes the source to a temp file
     named for its language, runs
     `truent scan <file> --chain <engine> --output json --no-color`, parses
     stdout, maps `violations[]` to `Finding` rows, and in one transaction
     deletes old findings, inserts new ones, sets `status='complete'`,
     `completedAt`, `durationMs`, `sourceContent=NULL`.
  5. Browser sees `status:"complete"` and navigates to `/reports/<id>`, which
     GETs `/api/scans/<id>` again and renders `scan.findings`.

2.4 Trust boundaries

  - Everything from the browser is untrusted: body, query, headers (except
    the session cookie after verification), `Origin`.
  - The engine's stdout is trusted only structurally: it is parsed as JSON and
    every field is validated before storage (section 12). Unknown values fall
    back to safe defaults; they never raise.
  - Stripe webhook bodies are trusted only after signature verification with
    `STRIPE_WEBHOOK_SECRET`.
  - Civic identities are trusted only after the ID token's signature is
    verified against Civic's JWKS and its `aud`/`iss`/`exp` claims pass.
  - Submitted source is attacker-controlled input to the engine. It is written
    to a private temp dir (mode 0700, file mode 0600), never interpolated into
    a shell, and the engine is run with a wall-clock timeout and an output
    size cap. Production SHOULD run workers in a sandbox with no cloud
    metadata access (section 17.6).

3. THE ENGINE: WHAT THE BACKEND DEPENDS ON
================================================================================

The backend treats the engine as a black box with a JSON contract. This
section records that contract exactly as truent 0.6.0 implements it. The
backend MUST NOT depend on anything about the engine that is not listed here.

3.1 Binary and invocation

  - Path comes from `TRUENT_BINARY` (default: `truent` on PATH).
  - Always invoked with an argument list (`subprocess.run([...])`), never a
    shell string.
  - Environment passed to the engine: the worker's environment plus
    `NO_COLOR=1`. The engine additionally honours these variables (none are
    required by the backend):
        SOLC_PATH               path to a solc binary (EVM AST rule only)
        TRUENT_SOLC_VERSION     solc version to download if none is present
        TRUENT_HOME             cache directory (solc downloads, skill sources)
        COLORTERM, HOME, PATH, USERPROFILE   platform/terminal detection
  - The engine prints a banner to stderr when stderr is a TTY. Workers MUST
    capture stderr (so it is never a TTY) and MUST NOT parse it.

3.2 Commands the backend uses

  scan      the only command the worker runs per submission
  taxonomy  `--format json` — detector metadata for the catalog endpoint
  pathways  `--format json` — 21 pathways for the catalog endpoint
  exposure  `<path> --format json` — used only for its `known_chains` (attack
            chains); run against `examples/foundry` in the repository, as the
            existing `web/scripts/sync-catalog.mjs` does
  doctor    `--format json` — engine self-test for `/api/health/engine`
  --version — recorded in the catalog as `generated_from`

  The full CLI surface (every command and flag) is in Appendix A for
  reference; the worker MUST NOT expose any other command to user input.

3.3 `truent scan` — exact invocation used by the worker

  argv:
    [TRUENT_BINARY, "scan", <file_name>, "--chain", <engine>,
     "--output", "json", "--no-color"]
  cwd:      the per-scan temp directory (so reported paths are bare file
            names like `app.py`, not temp paths — PRESERVE)
  timeout:  300 s wall clock (PRESERVE: the Node worker uses 5 min)
  stdout:   capped at 20 MiB (PRESERVE: `maxBuffer: 20 * 1024 * 1024`)
  stderr:   captured, discarded except in debug logs (never contains source)

  <engine> is one of: evm | solana | move | soroban | general
  (`auto` exists but the worker never uses it; the language already decides
  the engine.)

3.5 Exit codes of `truent scan`

  0   completed; either no violations, or none crossed the gate
  1   completed; at least one violation at or above `--fail-on` (default
      `critical`) was PROVEN (or `--fail-on-leads` was given). stdout still
      holds the full JSON report. PRESERVE: the worker treats exit 1 WITH
      non-empty stdout as a successful scan, not a failure.
  2   usage/argument error (from clap), or an explicit error exit in a few
      commands. stdout is empty or not JSON.
  other / signal / timeout   engine crash or killed. Treat as scan failure.

  Rule for the worker: if stdout parses as JSON with a `violations` array,
  the scan succeeded regardless of exit code. If stdout is empty or not JSON,
  the scan failed; the error message is the first 1000 chars of a generic
  description plus the exit code (never stderr verbatim in the API response,
  because stderr can echo user input).

3.6 The honesty contract (evidence)

  Every engine finding carries `evidence`:
    "lead"    a static inference: a pattern or dataflow the engine traced in
              source. Not demonstrated by execution. This is the default and
              is what every static detector emits.
    "proven"  observed on the wire (`truent probe`) or produced by a solver
              (`truent symbolic`): a concrete witness exists.

  Since the dashboard only runs `truent scan` (static engines), every finding
  it stores will be `lead` in practice. The backend MUST still store and
  return whatever the engine says and MUST default to `lead` for anything
  else. The frontend counts `proven` findings and shows the label; do not
  invent `proven`.

3.7 Exploitability

  A per-finding rating computed by the engine from the detector's attack
  profile (vector, prerequisite, victim interaction, impact) and its evidence:
    likely       reachable from the network by anyone, nothing in hand — or observed live
    possible     reachable from the network with a common precondition
    unlikely     needs a foothold, a condition, or a victim's action
    theoretical  requires privileged access or an unusual condition

  Scoring (engine `truent_core::exposure::rate`): vector network=3,
  adjacent=2, local=1; prereq authenticated −1, condition −1, privileged −2;
  interaction required −1; proven +1; ≥3 likely, 2 possible, 1 unlikely,
  ≤0 theoretical. `exploit_reasons` lists the reasons applied. The backend
  stores the rating and shows the reasons as `impact` (section 12).

3.8 Languages → engine → file name (PRESERVE exactly)

  The engine's general analyzer classifies files by NAME (`Dockerfile`,
  `*.tf`, `*.py`, …), so the worker MUST write the submission under a file
  name the detectors recognise:

    language     engine     file name         group
    ---------    -------    ---------------   ------------------
    solidity     evm        contract.sol      Smart contracts
    rust         solana     program.rs        Smart contracts
    soroban      soroban    contract.rs       Smart contracts
    move         move       module.move       Smart contracts
    python       general    app.py            Application code
    javascript   general    app.js            Application code
    typescript   general    app.ts            Application code
    go           general    main.go           Application code
    shell        general    script.sh         Application code
    dockerfile   general    Dockerfile        Infrastructure
    terraform    general    main.tf           Infrastructure
    yaml         general    deployment.yaml   Infrastructure

  Exactly these 12 values are accepted by `POST /api/analyze`. Anything else
  is a 400.

3.11 `truent exposure <path> --format json`

    { "target": "...", "findings": [...], "accepted": [...],
      "chains": [ <completed chain hits> ], "known_chains": [ <12 chain definitions> ] }

  known_chains[i]: { "id", "name", "narrative", "tactics": [..], "steps": [{"role","any_of":[ids]}], "break_at": <int> }
  The backend uses only `known_chains` (Appendix D).

3.12 `truent doctor --format json`

  Exit 0 when all components are healthy, 1 otherwise. The backend's
  `/api/health/engine` runs it with a 60 s timeout and reports exit code,
  version and the parsed component list if JSON parsing succeeds. Doctor
  performs no network access.

3.13 Engine behaviours the backend relies on (and tests for)

  - Deterministic: same source + same engine version → same findings.
  - Findings are deduplicated on (invariant_id, file, line) inside the engine;
    the backend's `(scanId, fingerprint)` unique constraint is a second net.
  - Foundry test/script files (`*.t.sol`, `*.s.sol`) produce no findings.
    Irrelevant here because the worker names the file `contract.sol`.
  - Comments and string literals are stripped before detection; the
    `code_snippet` is restored to the user's original text.
  - `truent:allow` / `truent:allow <id>` on a line or the line above
    suppresses general-analyzer findings there. Users can use it in
    submissions; the backend does nothing special.
  - The engine never reads `.truent.toml` from the temp dir unless one is
    present; the worker MUST NOT create one, and MUST refuse a submission
    that tries to be one (irrelevant: the file name is fixed by language).

4. TECHNOLOGY DECISIONS
================================================================================

  Component            Choice                              Reasoning
  -------------------  ----------------------------------  ----------------------------------------------
  Language             Python 3.12+                        Stated requirement.
  Web framework        FastAPI 0.115+ on Starlette         Async, typed, OpenAPI for free, Pydantic v2 native.
  ASGI server          uvicorn (workers via a process      Standard; no gunicorn needed behind a reverse proxy.
                       manager or replicas)
  Validation           Pydantic v2                          Mirrors the zod schemas 1:1 (section 9).
  Database driver      asyncpg                              Native Postgres, `FOR UPDATE SKIP LOCKED` support.
  ORM / query layer    SQLAlchemy 2.x (async, Core + ORM)   Typed models; raw SQL where the claim query needs it.
  Migrations           Alembic, baselined on the Prisma     Prisma stays authoritative for the frontend's
                       schema (section 7.6)                 generated client; Alembic owns new backend changes.
  Password hashing     `bcrypt` package (cost 10)           MUST verify existing `$2b$10$` hashes made by the
                                                            Node `bcrypt` library. Same algorithm, same format.
  Session tokens       PyJWT, HS256, 7-day expiry           Frontend middleware verifies with `jose` (19.3).
  Wallet signatures    `eth-account` (`Account.recover_message`, `encode_defunct`)  EIP-191 `personal_sign` recovery, same as ethers `verifyMessage`.
  Civic verification   `PyJWT` + `PyJWKClient` against       Standard OIDC ID-token verification; no Civic SDK
                       Civic's JWKS                          exists for Python (section 8.5).
  Stripe               `stripe` official SDK                 Webhook signature verification + Checkout Sessions.
  HTTP client          `httpx` (async)                       Civic JWKS/userinfo, JSON-RPC for crypto verify.
  IDs                  `cuid2` package                       Existing rows use Prisma cuid (`c…`, 25 chars); any
                                                            unique TEXT works, cuid2 keeps URLs the same shape.
  Logging              `structlog` → JSON lines              Redaction processor (section 16.2).
  Settings             `pydantic-settings`                   Typed env parsing with validation at startup.
  Tests                `pytest`, `pytest-asyncio`, `httpx.AsyncClient`, `testcontainers[postgres]` (or compose)
  Lint/format          `ruff`, `mypy --strict` on `truent_backend/`

  Not used, deliberately:
  - Celery/RQ/Redis: the existing design uses PostgreSQL as the queue with
    `SKIP LOCKED`; adding a broker adds an operational dependency for no gain
    at this scale. PRESERVE the SQL queue.
  - An ORM-generated schema: the schema is fixed by Prisma migrations; models
    are written to match it, not the other way around.
  - Django: too much for a JSON API with 15 routes.

7.4 Time and ID semantics

  - All TIMESTAMP(3) columns are naive timestamps that Prisma writes in UTC.
    SQLAlchemy models use `DateTime(timezone=False)`; the backend always
    writes `datetime.now(timezone.utc).replace(tzinfo=None)` and always
    serialises as UTC ISO-8601 with 3 fractional digits and `Z`
    (`2026-09-24T16:36:42.444Z`). Helper: `iso_ms(dt)`.
  - `updatedAt` MUST be set by the backend on INSERT and on every UPDATE
    (SQLAlchemy `onupdate=utcnow` + explicit default). Forgetting this raises
    a NOT NULL violation on insert — a test covers it.
  - IDs: `new_id()` returns a cuid2 string. Existing rows have Prisma cuid
    (`cmufr7zmg0000d24ai23ffyfl`). Both are opaque TEXT; the frontend never
    parses them.

7.6 Migrations policy

  - Alembic revision `0001_baseline` contains NO DDL. Its `upgrade()` is a
    no-op; it exists so `alembic stamp 0001_baseline` marks a database that
    already has the Prisma schema. `alembic upgrade head` on a fresh database
    MUST fail with a clear message telling the operator to run
    `npx prisma migrate deploy` in `web/` first. (Reasoning: two migration
    tools must not both create the same tables. Prisma created them; Alembic
    only adds.)
  - Any later backend-only change is an Alembic revision AND a matching
    Prisma migration file so the frontend's generated client stays in sync.
    Until the frontend stops using Prisma (it still does for nothing after
    this migration — see 19.4), keep both.
  - `alembic upgrade head` runs in a deploy step, never inside `main.py`.

7.7 Connection settings

  - Pool: `pool_size=5`, `max_overflow=10` per API replica; the worker uses a
    pool of 2 (one for the claim loop, one spare).
  - Statement timeout: `SET statement_timeout = 15000` for API sessions
    (via `connect_args={"server_settings": {"statement_timeout": "15000"}}`);
    the worker's claim connection uses 5000, the write transaction 30000.
  - Every request gets one session via the `get_session` dependency;
    commit on success, rollback on exception.

7.8 Data retention

  - `Scan.sourceContent` is deleted (set NULL) when a scan completes or
    fails terminally (PRESERVE). It is also cleared for rows the stale-reclaim
    sweep marks failed. A retained submission is a stored secret risk.
  - `AuthNonce` rows expire after 5 minutes; a periodic delete of
    `expiresAt < now()` SHOULD run (the worker does it once per poll cycle
    every 60 s). Not doing so is harmless (the verify step checks expiry),
    but the table grows.
  - Findings and scans are kept indefinitely (no retention policy exists
    today). Deleting a User cascades to Scans and Findings.

8. IDENTITY, SESSIONS AND AUTHENTICATION
================================================================================

8.1 What exists today (to be replaced)

  NextAuth 4 with three `CredentialsProvider`s (`civic`, `credentials`,
  `wallet`), JWT sessions (7 days) in NextAuth's own encrypted cookie, a
  Prisma adapter, and a Next middleware that redirects unauthenticated
  requests for `/dashboard/*`, `/reports/*`. The session object exposed to the
  frontend is:
      session.user = { id, name, email, image, walletAddress?, provider? }
  where `provider` ∈ {"civic","credentials","wallet"}.

8.2 Python design: session token

  - Format: JWT, HS256, key = `SESSION_SECRET`.
  - Claims:
        sub      user id
        email    user.email (may be an 0x address for wallet users)
        name     user.name or null
        picture  user.image or null
        provider "credentials" | "wallet" | "civic"
        wallet   lowercased address for wallet sessions, else absent
        iat, exp (exp = iat + SESSION_TTL_SECONDS), jti (uuid4)
        iss      "truent-backend", aud "truent-web"
  - Transport: cookie `truent_session`; `HttpOnly`; `SameSite=Lax`;
    `Secure` when APP_URL is https; `Path=/`; `Max-Age=SESSION_TTL_SECONDS`.
  - Verification: `jwt.decode(token, key, algorithms=["HS256"], audience="truent-web", issuer="truent-backend")`.
    Any failure → 401. The backend MUST also check the user still exists
    (one indexed lookup by id) so a deleted account cannot keep using a token.
  - No refresh endpoint. A session lasts 7 days from sign-in, as today.
  - Sign-out clears the cookie (`Max-Age=0`). There is no server-side
    revocation list in v1 (PRESERVE: NextAuth JWTs had none either). `jti`
    is included so a denylist can be added later without changing the token.

  Reasoning: HS256 (not NextAuth's JWE) so the Next.js middleware can verify
  the cookie with `jose.jwtVerify` and the same secret — see 19.3.

8.3 `current_user` dependency

    async def current_user(request, session=Depends(get_session), settings=Depends(get_settings)) -> UserWithSubscription:
        token = request.cookies.get(settings.session_cookie_name)
        if not token: raise HTTPException(401, {"error": "Unauthorized"})
        try: claims = verify_session(token, settings)
        except InvalidToken: raise HTTPException(401, {"error": "Unauthorized"})
        user = await session.get(User, claims["sub"], options=[selectinload(User.subscription)])
        if user is None: raise HTTPException(401, {"error": "Unauthorized"})
        return user

  PRESERVE the response body `{"error":"Unauthorized"}` with status 401 for
  every protected route. (The current code looks users up by email; looking
  up by id is stricter and equivalent because email is unique.)

8.4 Provider: email + password

  Sign-up (POST /api/auth/signup) — PRESERVE all rules:
    - body: `{email, password, name}`; email must be a valid address; password
      12–128 chars; name trimmed, 1–100 chars.
    - email is trimmed and lowercased before lookup and storage.
    - if a user with that email exists → 400 `{"error":"Email already in use"}`.
      (Reasoning note: this is an enumeration oracle by design of the current
      product; keep it, it is what the UI shows.)
    - hash with bcrypt cost 10; store; return 201 with the user WITHOUT the
      password field: `{id,name,email,emailVerified,civicId,image,createdAt,updatedAt}`.
    - Sign-up does NOT issue a session; the frontend calls sign-in next.

  Sign-in (POST /api/auth/signin) — replaces NextAuth's credentials callback:
    - body `{email, password}`; both required else 401.
    - lookup by email as given (PRESERVE: NextAuth looked up the raw value;
      the backend SHOULD lowercase+trim, which is a superset because sign-up
      lowercases).
    - ALWAYS run `bcrypt.checkpw` — against the stored hash if the user
      exists, else against a precomputed dummy hash — so timing does not
      reveal whether the account exists (PRESERVE).
    - On success: issue session with provider "credentials"; return 200
      `{"ok":true, "url":"/dashboard", "user": <session user>}` and the
      Set-Cookie header. On failure: 401 `{"error":"Invalid email or password"}`.

    Dummy hash: computed once at import: `bcrypt.hashpw(b"truent-timing-safety-dummy", bcrypt.gensalt(10))`.

8.5 Provider: Civic

  What Civic gives the browser: after `civic.signIn()` in the frontend, the
  Civic Next.js plugin's routes (`/api/civic/*`, which STAY in the Next.js
  app because they are part of `@civic/auth/nextjs`) set Civic's own session
  cookies, and the React SDK exposes `useUser()`. Today NextAuth's `civic`
  provider calls `getUser()` from `@civic/auth/nextjs` server-side, which
  verifies those cookies and returns `{id, email?, name?, username?, picture?}`.

  Python design (POST /api/auth/civic):
    - The frontend, after `civic.signIn()` resolves, obtains the Civic ID
      token from the SDK (`useUser().idToken` / `getUser()`; the exact
      accessor MUST be confirmed against `@civic/auth` 0.15.x docs at
      implementation time) and POSTs `{ "id_token": "<jwt>" }`.
    - The backend verifies the token as an OIDC ID token:
        issuer  = CIVIC_ISSUER  (confirm the exact `iss` value from
                  `<issuer>/.well-known/openid-configuration` at implementation time)
        audience = NEXT_PUBLIC_CIVIC_CLIENT_ID
        signature via JWKS from the discovery document (`PyJWKClient`, cached 1 h)
        exp/nbf/iat with 60 s leeway
      Any failure → 401 `{"error":"Civic sign-in failed"}`.
    - Identity fields taken from claims: `sub` → civic.id; `email`; `name`;
      `preferred_username` → username; `picture`.
    - `resolve_civic_user` — PRESERVE the order exactly:
        1. user with `civicId == sub` → return it.
        2. else if email present: user with that (lowercased) email → link:
           set civicId, emailVerified=now, image = existing image or picture;
           return it. (A password user keeps their scans and plan.)
        3. else create: civicId=sub, email (may be null), emailVerified = now
           if email else null, name = name or username or email local-part or
           `Civic <first 6 of sub>`, image = picture or null.
    - Issue a session with provider "civic". Return 200 `{"ok":true,"url":"/dashboard","user":…}`.
    - If Civic is disabled (empty client id) → 404 `{"error":"Not found"}`.
    - Sign-out order PRESERVE: the frontend ends the backend session first
      (POST /api/auth/signout), then Civic's, then navigates.

  Security note: the backend MUST NOT accept a profile object from the
  request body (the current provider reads nothing from the body for exactly
  this reason). Only a verifiable token is accepted.

8.6 Provider: Web3 wallet

  Challenge (POST /api/auth/wallet-nonce) — PRESERVE byte-for-byte:
    - body `{address}`; must match `^0x[a-fA-F0-9]{40}$` else 400
      `{"error":"Invalid wallet address"}`.
    - address = lowercased.
    - nonce = 24 random bytes as 48 lowercase hex chars (`secrets.token_hex(24)`).
    - message = "Truent sign-in\nAddress: " + address + "\nNonce: " + nonce
      (three lines, `\n` separators, no trailing newline).
    - upsert AuthNonce(address, nonceHash=sha256(nonce).hexdigest(), expiresAt=now+5min).
      On conflict (address exists) update nonceHash and expiresAt: one
      outstanding challenge per address; a new request replaces the old one.
    - return 200 `{"message": <message>, "expiresIn": 300}`.
    - DB failure → 500 `{"error":"Unable to create nonce"}`.

  Verify (POST /api/auth/wallet) — replaces NextAuth's wallet callback:
    - body `{address, message, signature}`; any missing → 401.
    - normalized = address.lower().
    - message MUST fully match
        r"^Truent sign-in\nAddress: (0x[a-f0-9]{40})\nNonce: ([a-f0-9]{48})$"
      and group 1 MUST equal normalized. (Note: lowercase hex only — the
      message was built from the lowercased address.)
    - load AuthNonce by normalized; require it exists, `expiresAt > now`,
      and `nonceHash == sha256(group 2)`.
    - recover the signer:
        from eth_account import Account
        from eth_account.messages import encode_defunct
        signer = Account.recover_message(encode_defunct(text=message), signature=signature)
      `signer.lower()` MUST equal normalized. Any exception (bad signature
      length, non-hex) → failure.
      This is EIP-191 `personal_sign` recovery, identical to ethers
      `verifyMessage(message, signature)`. The frontend signs the hex-encoded
      UTF-8 bytes of the same message; MetaMask's `personal_sign` prefixes
      "\x19Ethereum Signed Message:\n<len>" over the same bytes, so
      `encode_defunct(text=message)` matches.
    - DELETE the AuthNonce row (single use). Do this before issuing the
      session, inside the same transaction as the user upsert.
    - find user with `email == normalized`; if none, create
      `{email: normalized, name: "Wallet " + address[:6]}` (PRESERVE:
      `credentials.address.slice(0, 6)` uses the ORIGINAL casing of the
      address as submitted, e.g. "Wallet 0xAbC1"; keep that).
    - Issue session with provider "wallet" and `wallet` = normalized.
      Return 200 `{"ok":true,"url":"/dashboard","user":…}`.
    - Any failure → 401 `{"error":"Wallet signature could not be verified"}`.
      Never say which step failed.

  Sequence (wallet):

    Browser                          Backend                          DB
    ───────                          ───────                          ──
    eth_requestAccounts → [addr]
    POST /api/auth/wallet-nonce {address}
                                     validate, lowercase, nonce, message
                                     upsert AuthNonce(hash, +5m)  ──────▶
    ◀── {message, expiresIn:300}
    personal_sign(hex(message), addr) → signature
    POST /api/auth/wallet {address, message, signature}
                                     regex + address match
                                     load nonce, expiry, hash   ◀──────
                                     recover signer == address
                                     delete nonce                ──────▶
                                     find/create User(email=addr)──────▶
                                     issue JWT, Set-Cookie
    ◀── 200 {ok, url:"/dashboard"}
    location = /dashboard  (Next middleware verifies cookie)

8.8 CSRF

  - All cookies are `SameSite=Lax`, which blocks cross-site POST/PATCH with
    the cookie attached in current browsers.
  - Defence in depth (MUST): for every request with method POST, PATCH, PUT,
    DELETE that carries the session cookie, if an `Origin` header is present
    it MUST equal APP_URL's origin (scheme+host+port), else 403
    `{"error":"Forbidden"}`. If `Origin` is absent, `Sec-Fetch-Site` MUST be
    absent or `same-origin`/`none`. Exempt: `/api/payment/webhook` (Stripe,
    no cookie, signature-verified) and `/api/health*`.
  - No CSRF token is required (NextAuth's `csrfToken` form field disappears
    with NextAuth). The frontend's `signIn()` calls become plain `fetch` POSTs
    (19.3).

8.9 Route protection for pages

  Page-level protection (`/dashboard/*`, `/reports/*`) stays in the Next.js
  middleware, rewritten to verify the backend's cookie (19.3). The backend
  protects its own API routes with `current_user`; it does not know about
  pages. `/api/auth/session` is intentionally NOT protected.

9.0 Conventions for every route

  - Base path `/api`. The reverse proxy routes `/api/*` to the Python service
    EXCEPT `/api/civic/*`, which stays with Next.js (Civic's plugin routes).
  - Request bodies are JSON (`Content-Type: application/json`). A body that
    is not valid JSON → 400 `{"error":"Invalid JSON"}`.
  - Validation errors → 400 `{"error": "<first issue message>"}` — PRESERVE
    the shape: one string, the first problem only (the current code returns
    `error.issues[0].message`). Pydantic messages differ from zod's; where the
    frontend displays the message verbatim (sign-up, analyze), use the exact
    strings listed per route via custom validators.
  - Every error response is `{"error": string}` and nothing else. Never
    include exception text, stack traces, SQL, or user input in `error`.
  - Success responses are the exact objects documented below; extra fields
    are allowed only where marked "extensible".
  - Unauthenticated access to a protected route → 401 `{"error":"Unauthorized"}`.
  - Unknown route → 404 `{"error":"Not found"}`. Method not allowed → 405 same shape.
  - Unhandled exception → 500 `{"error":"Internal server error"}` + a log
    line with a request id.
  - `Content-Type: application/json; charset=utf-8` on all responses.
  - Response header `X-Request-Id` echoes the inbound header or a new uuid4.

9.10 POST /api/analyze
--------------------------------------------------------------------------------
  Auth: required.
  Request:
    { "code": string, "language"?: string, "projectName"?: string }
  Validation (PRESERVE messages and limits):
    code         non-empty                     → "Code is required"
                 ≤ 500000 characters           → "Code exceeds maximum size"
    language     one of the 12 ids (3.8); default "solidity" when absent
                 → invalid: "Invalid option: expected one of ..." (any clear message; the UI never sends an invalid one)
    projectName  optional; trimmed; 1..120     → too long: "Project name must be at most 120 characters"
  Order of checks (PRESERVE — quotas are checked BEFORE body validation in
  the current code, so an over-quota user gets 429/403 even with a bad body):
    1. auth → 401
    2. per-minute: count Scan where userId = me and createdAt >= now-60s;
       if ≥ 5 → 429 {"error":"Rate limit exceeded. Please wait before submitting another scan."}
       with header `Retry-After: 60`
    3. monthly: monthStart = first day of current month 00:00:00 UTC;
       activePlan = subscription.plan if subscription.status == "active" else None;
       used = count Scan where userId = me and createdAt >= monthStart;
       if used ≥ monthly_scan_limit(activePlan) → 403 {"error":"Monthly scan quota exceeded"}
    4. parse + validate body → 400
    5. insert Scan { userId, projectName: projectName or "Untitled scan",
       sourceType "code", sourceContent code, language, status "queued",
       attempts 0, startedAt now, createdAt now, updatedAt now }
  Response 202:
    { "success": true, "scanId": "<id>", "status": "queued", "createdAt": "<iso>" }
    Header: `Location: /api/scans/<id>`
  Errors: 500 {"error":"Unable to queue scan"}.
  Notes:
    - `code` size is measured in characters (JS `.length` on a UTF-16 string
      counts code units; Python `len` counts code points; the difference only
      matters for astral characters — accept the tiny drift).
    - The body limit at the ASGI layer MUST be ≥ 2 MiB so a 500k-char UTF-8
      submission fits; set the reverse proxy `client_max_body_size` to 4m.
  Tests:
    - 202 with Location header; row has status queued and sourceContent = code.
    - 6th submission inside 60 s → 429 with Retry-After: 60.
    - free user with 5 scans this month → 403; user with an active
      professional subscription and 5 scans → 202.
    - subscription with status "past_due" counts as no plan → 403 at 5.
    - empty code → 400 "Code is required"; 500001 chars → 400 "Code exceeds maximum size".
    - missing language → stored as "solidity".
    - projectName absent → "Untitled scan"; whitespace-only → 400 (min 1 after trim).
    - month boundary: a scan created at 23:59:59.999Z on the last day does not
      count toward the next month.

  No cookie; exempt from the Origin check.
  Processing (PRESERVE):
    - if header or secret missing → 503 {"error":"Webhook is not configured"}
    - event = stripe.Webhook.construct_event(raw_body, sig, secret); failure → 400 {"error":"Invalid signature"}
      (raw body MUST be the exact bytes received — read `await request.body()`; do not re-serialise)
    - "checkout.session.completed":
        userId = metadata.userId; plan = metadata.planId
        if userId and plan is a known plan and session.subscription:
          upsert Subscription by userId:
            provider "stripe", providerCustomerId str(customer or ""),
            providerSubscriptionId str(subscription), plan, status "active"
    - "customer.subscription.updated" | "customer.subscription.deleted":
        UPDATE Subscription WHERE providerSubscriptionId = sub.id SET
          status = sub.status, cancelAtPeriodEnd = sub.cancel_at_period_end,
          currentPeriodEnd = from items.data[0].current_period_end (seconds → datetime)
    - any other type: ignored
  Response 200: { "received": true }
  Idempotency (SHOULD, improvement): store processed `event.id` in a small
  table `StripeEvent(id TEXT PK, receivedAt)` (Alembic revision 0002) and
  return 200 without re-applying a duplicate. Stripe retries on non-2xx;
  the handlers above are idempotent by construction (upsert/update), so this
  is belt-and-braces.
  Tests: construct events with `stripe.WebhookSignature` test helpers;
  completed → subscription active; updated with status "past_due" → row
  updated; bad signature → 400; unconfigured → 503; unknown type → 200.

9.16 POST / PATCH /api/payment/crypto
--------------------------------------------------------------------------------

  POST creates a non-persisted "payment request" object; PATCH verifies a
  transaction on-chain and returns success but does NOT provision a plan.
  Both require auth.

  POST request:
    { "planId": string, "planName": string, "priceUSD": number > 0, "currency"?: string, "walletAddress": "0x…40hex" }

10. QUOTAS AND RATE LIMITS
================================================================================

10.1 Per-user scan burst limit (PRESERVE)

  5 scans per rolling 60 seconds per user, computed by counting Scan rows
  (`createdAt >= now - 60s`), not by an in-memory counter, so it holds across
  API replicas and restarts. Exceeding it → 429 with `Retry-After: 60`.

10.2 Monthly quota (PRESERVE)

    def monthly_scan_limit(plan: str | None) -> int:
        if plan and plan in PLANS: return PLANS[plan].scans_per_month   # professional → 10000
        return 5                                                          # free

  Counted from the first of the current month 00:00 UTC. A subscription
  counts only while `status == "active"` (Stripe statuses "trialing",
  "past_due", "canceled" etc. do NOT count — PRESERVE the strict equality).

10.3 Counting semantics

  Failed and queued scans count toward both limits (a row exists). This is
  the current behaviour; do not "refund" failed scans in v1.

10.4 Unauthenticated endpoints (new, SHOULD)

  Sign-up, sign-in, wallet-nonce, wallet, civic: 30 requests per IP per
  minute, sign-up 10 per IP per hour. Implementation: a fixed-window counter
  keyed by (route, client IP) in Postgres table `RateLimit(key TEXT PK,
  windowStart TIMESTAMP, count INT)` — no Redis. Client IP comes from
  `X-Forwarded-For` only when `TRUST_PROXY=true` (add to Settings; default
  false → use the socket peer). Exceeding → 429 {"error":"Too many requests"}.

11. SCAN PIPELINE AND WORKER
================================================================================

11.1 Scan state machine

    queued ──claim──▶ processing ──success──▶ complete
       ▲                  │
       │                  ├──failure, attempts < max──▶ queued   (error set, claimedAt/workerId cleared)
       │                  │
       │                  └──failure, attempts ≥ max──▶ failed   (completedAt set, sourceContent NULL)
       │
       └── stale reclaim: processing AND claimedAt < now-10min AND attempts < max → claimable again
           processing AND claimedAt < now-10min AND attempts ≥ max → failed
           ("Worker stopped before completing the scan"), sourceContent NULL

  Invariants:
    - `attempts` only increases; incremented at claim time (PRESERVE).
    - A row is `complete` only after findings were replaced atomically.
    - `sourceContent` is NULL for every `complete` or `failed` row.
    - `error` is ≤ 1000 characters and never contains engine stderr verbatim
      or submitted source.

11.2 Claim query (PRESERVE semantics; run as two statements on one connection)

  Sweep (before each claim attempt):
    UPDATE "Scan"
    SET "status" = 'failed', "error" = 'Worker stopped before completing the scan',
        "completedAt" = NOW(), "sourceContent" = NULL, "updatedAt" = NOW()
    WHERE "status" = 'processing' AND "attempts" >= :max_attempts
      AND "claimedAt" < NOW() - make_interval(mins => :stale_minutes);

  Claim:
    UPDATE "Scan"
    SET "status" = 'processing', "claimedAt" = NOW(), "workerId" = :worker_id,
        "attempts" = "attempts" + 1, "updatedAt" = NOW()
    WHERE "id" = (
      SELECT "id" FROM "Scan"
      WHERE "attempts" < :max_attempts
        AND ("status" = 'queued'
         OR ("status" = 'processing' AND "claimedAt" < NOW() - make_interval(mins => :stale_minutes)))
      ORDER BY "createdAt" ASC
      FOR UPDATE SKIP LOCKED
      LIMIT 1
    )
    RETURNING *;

  Both statements run in autocommit (each is its own transaction). Multiple
  workers are safe: SKIP LOCKED means two workers never claim the same row.

11.3 Worker main loop

    async def main(settings):
        worker_id = settings.hostname or f"worker-{uuid4()}"
        stopping = False
        install SIGTERM/SIGINT handlers → stopping = True
        once = "--once" in sys.argv
        last_nonce_sweep = 0
        while not stopping:
            scan = await claim(worker_id)
            if scan is None:
                if once: break
                if time() - last_nonce_sweep > 60: await delete_expired_nonces(); last_nonce_sweep = time()
                await asyncio.sleep(poll_ms / 1000); continue
            try:
                await run_scan(scan)
            except Exception as e:
                log.error("scan_failed", scan_id=scan.id, error=type(e).__name__)
                await fail(scan, e)
            if once: break
        await engine.dispose()

  - `--once` processes at most one scan and exits (PRESERVE; used by tests).
  - On SIGTERM the loop finishes the current scan (up to the engine timeout)
    before exiting; the process manager SHOULD allow ≥ 330 s grace.
  - Exit code 1 if the loop crashes (PRESERVE `process.exitCode = 1`).

11.4 Running one scan

    async def run_scan(scan):
        chain = chain_for(scan.language); file_name = file_name_for(scan.language)
        if not chain or not file_name or not scan.source_content:
            raise ScanInputError("Scan source or language is invalid")      # PRESERVE message
        work = tempfile.mkdtemp(prefix="truent-scan-")                      # mode 0700 by default
        started = monotonic()
        try:
            path = os.path.join(work, file_name)
            with open(os.open(path, os.O_WRONLY|os.O_CREAT|os.O_EXCL, 0o600), "w", encoding="utf-8") as f:
                f.write(scan.source_content)
            result = await run_engine([binary, "scan", file_name, "--chain", chain, "--output", "json", "--no-color"],
                                      cwd=work, timeout=settings.scan_timeout_seconds,
                                      stdout_cap=settings.scan_stdout_max_bytes, env={**os.environ, "NO_COLOR": "1"})
            # PRESERVE: non-zero exit with stdout is a valid report (proven finding crossed the gate)
            if not result.stdout.strip():
                raise EngineError(f"Analyzer exited with code {result.returncode}")
            report = json.loads(result.stdout)
            if not isinstance(report.get("violations"), list):
                raise EngineError("Analyzer returned an invalid report")    # PRESERVE message
            findings = [map_finding(scan.id, v) for v in report["violations"]]
            async with session.begin():
                await session.execute(delete(Finding).where(Finding.scan_id == scan.id))
                session.add_all([Finding(**f) for f in findings])
                await session.execute(update(Scan).where(Scan.id == scan.id).values(
                    status="complete", completed_at=utcnow_naive(),
                    duration_ms=int((monotonic()-started)*1000), error=None, source_content=None,
                    updated_at=utcnow_naive()))
        finally:
            shutil.rmtree(work, ignore_errors=True)

  Duplicate fingerprints within one report: the engine dedups on
  (invariant_id, file, line) and the fingerprint includes severity, so
  collisions are not expected; the worker MUST still dedupe the list by
  fingerprint before insert (keep first) so the UNIQUE constraint can never
  fail the whole scan.

  `run_engine` (engine/runner.py):
    - `asyncio.create_subprocess_exec(*argv, cwd=cwd, stdin=DEVNULL, stdout=PIPE, stderr=PIPE, env=env)`
    - read stdout incrementally; if it exceeds `stdout_cap`, kill the process
      and raise EngineError("Analyzer output exceeded limit").
    - `asyncio.wait_for(..., timeout)`; on timeout kill (SIGKILL after 5 s
      grace following SIGTERM) and raise EngineError("Analyzer timed out").
    - stderr is read to EOF and discarded (kept only in debug logs, truncated
      to 4 KiB, and never included in `Scan.error`).

11.5 Failure path (PRESERVE)

    async def fail(scan, error):
        retry = scan.attempts < settings.scan_max_attempts
        values = dict(status="queued" if retry else "failed",
                      error=str(error)[:1000] if isinstance(error, (ScanInputError, EngineError)) else "Analyzer failed",
                      claimed_at=None, worker_id=None, updated_at=utcnow_naive())
        if not retry: values.update(completed_at=utcnow_naive(), source_content=None)
        UPDATE Scan SET values WHERE id = scan.id

  Difference from the Node worker, deliberate: the Node code stores
  `error.message` for ANY error (which could include a Postgres error
  string). The Python worker stores the message only for the two typed
  errors it raises itself and "Analyzer failed" for everything else.

11.7 Concurrency and sizing

  - One worker process handles one scan at a time (PRESERVE). Scale by
    replicas. A scan takes ~20 ms–2 s for typical inputs; the 3000-file
    stress test in `tests/load/stress-scan.sh` is for the CLI, not the
    dashboard path.
  - Memory: the engine is a single static binary; budget 512 MiB per worker
    replica plus the 20 MiB stdout cap.
  - The worker MUST NOT run with the API in the same process.

11.8 Sandboxing (SHOULD, production)

  Run worker replicas in a container with: read-only root filesystem except
  `/tmp`; no network egress (the engine needs none for `scan`; solc download
  for the optional EVM AST rule is disabled without network and the engine
  falls back silently — acceptable); no cloud metadata access; `nproc`/CPU
  limit; `TMPDIR` on a tmpfs sized ≥ 64 MiB. The engine is Rust with
  `#![deny(unsafe_code)]` in every crate, but the input is attacker-chosen.

12. FINDING MAPPING (engine JSON → database → API)

12.1 `map_finding(scan_id, v) -> dict` — pure function, PRESERVE exactly

    SEVERITIES = {"critical","high","medium","low","info"}
    EXPLOITABILITY = {"likely","possible","unlikely","theoretical"}

    def map_finding(scan_id: str, v: dict) -> dict:
        raw_sev = str(v.get("severity") or "low").lower()
        severity = raw_sev if raw_sev in SEVERITIES else "low"

        inv = v.get("invariant_id")
        invariant_id = inv if isinstance(inv, str) and inv else None
        title = v.get("title") or (invariant_id.replace("_", " ") if invariant_id else "security finding")
        description = str(v.get("message") or "Security issue detected")

        file = v.get("file") if isinstance(v.get("file"), str) and v.get("file") else None
        line = v.get("line") if isinstance(v.get("line"), int) and not isinstance(v.get("line"), bool) and v.get("line") > 0 else None
        if not file and isinstance(v.get("location"), str):
            m = re.match(r"^(.*):(\d+)$", v["location"])
            if m: file, line = m.group(1), (int(m.group(2)) or None)
            else: file = v["location"] or None
        location = f"{file} · Line {line}" if file and line else (file if file else None)

        evidence = "proven" if v.get("evidence") == "proven" else "lead"
        exploitability = v.get("exploitability") if v.get("exploitability") in EXPLOITABILITY else None
        fix = v.get("fix") if isinstance(v.get("fix"), str) and v.get("fix") else None
        verify = v.get("verify") if isinstance(v.get("verify"), str) and v.get("verify") else None
        recommendation = fix or v.get("recommendation") or "Review this finding and apply the relevant invariant guidance."
        reasons = [r for r in (v.get("exploit_reasons") or []) if isinstance(r, str)] if isinstance(v.get("exploit_reasons"), list) else []
        if reasons:
            impact = ("Proven. " if evidence == "proven" else "") + "; ".join(reasons)
        else:
            impact = "Proven: observed on the wire or produced by a solver." if evidence == "proven" else None

        fingerprint = hashlib.sha256(
            f"{severity}\0{invariant_id or title}\0{file or ''}\0{line or ''}".encode("utf-8")).hexdigest()

        return dict(
            scan_id=scan_id, severity=severity, title=title, description=description,
            location=location, line=line, impact=impact, recommendation=recommendation,
            fingerprint=fingerprint, invariant_id=invariant_id,
            chain=v.get("chain") if isinstance(v.get("chain"), str) else None,
            evidence=evidence, exploitability=exploitability, fix=fix, verify=verify,
            cwe=v.get("cwe") if isinstance(v.get("cwe"), str) and v.get("cwe") else None,
            snippet=v.get("code_snippet")[:2000] if isinstance(v.get("code_snippet"), str) and v.get("code_snippet") else None,
        )

  Subtleties that the tests in 18.2 pin down:
    - `line` of 0 is "unknown" → None; the location then has no " · Line".
    - `"{line or ''}"` in the fingerprint: None and 0 both become "" — matches
      the JS template literal `${line || ''}`.
    - The `location` regex is greedy on the file part so "a:b.sol:12" → file
      "a:b.sol", line 12 (same as JS).
    - `title` falls back to the invariant id with underscores replaced by
      spaces (NOT humanised/capitalised — the engine already sends `title`).
    - Booleans are not ints for `line` (Python `True` is an int; exclude it).

12.2 Field provenance table

  DB column       source in engine JSON                     notes
  --------------  ----------------------------------------  ------------------------------------------
  severity        severity (lowercased, validated)          fallback "low"

13.1 Plans (PRESERVE; `web/lib/plans.ts`)

    PLANS = {
      "professional": Plan(name="Professional", monthly_amount=49900, scans_per_month=10000),
    }
    FREE_SCANS_PER_MONTH = 5

  There is exactly one paid plan. Prices are server-side; the client never

13.2 Subscription lifecycle

  1. User clicks upgrade → frontend POSTs `/api/payment/create-checkout {planId:"professional"}`
     → backend creates a Stripe Checkout Session (mode subscription) with
     `metadata.userId` and `metadata.planId` → returns the hosted URL →
     frontend redirects.
  2. Stripe → `/api/payment/webhook` `checkout.session.completed` → backend
     upserts `Subscription{userId, provider:"stripe", providerCustomerId,
     providerSubscriptionId, plan, status:"active"}`.
  3. Stripe → `customer.subscription.updated` on renewals, payment failures
     (`past_due`), cancellation scheduling (`cancel_at_period_end`) →
     backend updates status/cancelAtPeriodEnd/currentPeriodEnd by
     providerSubscriptionId.
  4. Stripe → `customer.subscription.deleted` → status "canceled" → quota
     falls back to free immediately (status != "active").

  Stripe must be configured (dashboard → Webhooks) to deliver exactly:
  `checkout.session.completed`, `customer.subscription.updated`,
  `customer.subscription.deleted` to `<APP_URL>/api/payment/webhook`
  (PRESERVE; from `web/BACKEND_DEPLOYMENT.md`).

13.3 Stripe API version

  Pin `stripe` SDK to a version whose default API version matches the one
  the current Node SDK (`stripe` ^22) uses, or set `stripe.api_version`
  explicitly, because `subscription.items.data[0].current_period_end` moved
  from the subscription object to the item in newer API versions (the Node
  code already reads it from `items.data[0]`). The Python handler MUST read
  `current_period_end` from `items.data[0]` and fall back to the top-level
  field if present, then convert seconds → naive UTC datetime.

13.4 Crypto payments (fail closed, PRESERVE)

  See 9.16. Summary of the rule: the route can VERIFY that a transaction
  from the claimed wallet to `PAYMENT_RECEIVER_ADDRESS` succeeded; it MUST
  NOT create or update a Subscription, and MUST return failure whenever the
  RPC URL or receiver address is not configured. Provisioning from crypto is
  blocked until amount and ERC-20 `Transfer` log verification are
  implemented (documented gap in `web/BACKEND_DEPLOYMENT.md`).

13.5 Refunds, proration, invoices

  Out of scope. Stripe's hosted customer portal can be linked from the
  frontend later; the backend would add `POST /api/payment/portal` creating
  a `billing_portal.Session` for `providerCustomerId`.

15. SECURITY REQUIREMENTS
================================================================================

15.1 Input handling

  - JSON bodies only; reject `Content-Type` other than `application/json`
    on JSON routes with 415 (except the Stripe webhook, which is read raw).
  - Maximum body 4 MiB at the proxy and 4 MiB in the app (Starlette does not
    limit by default; add a middleware that rejects `Content-Length` > 4 MiB
    with 413 {"error":"Payload too large"} and streams-and-aborts when
    absent).
  - Path parameters (`{id}`) are opaque strings; they are used only as SQL
    bind parameters. Never in file paths or shell.
  - All SQL goes through bound parameters. The two raw worker statements use
    `:name` binds. String formatting into SQL is forbidden.

15.2 Response headers (API)

  Every response: `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: strict-origin-when-cross-origin`,
  `Cache-Control: no-store` (except `/api/catalog*` and `/metrics`),
  `X-Frame-Options: DENY`, and a minimal
  `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`
  (the API serves no HTML; the header hardens error pages). The frontend
  keeps its own CSP from `web/next.config.js`:
    default-src 'self'; script-src 'self' 'unsafe-inline' https://js.stripe.com;
    style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com;
    img-src 'self' data: https:; connect-src 'self' https://api.stripe.com https://auth.civic.com;
    frame-src https://js.stripe.com https://checkout.stripe.com https://auth.civic.com;
    frame-ancestors 'none'; object-src 'none'; base-uri 'self'; form-action 'self'
  Because the API is same-origin (proxied under `/api`), `connect-src 'self'`
  already covers it; no frontend CSP change is needed.

15.3 CORS and Origin

  - Same-origin deployment is the design. `CORSMiddleware` allows only
    `CORS_ALLOWED_ORIGINS` (default APP_URL) with `allow_credentials=True`,
    methods GET/POST/PATCH/OPTIONS, headers Content-Type/X-Request-Id.
  - The Origin check for cookie-bearing state-changing requests (8.8) is a
    separate middleware and runs regardless of CORS configuration.

15.4 Secrets and logs

  - Never log: `Authorization`/`Cookie`/`Set-Cookie` headers, session
    tokens, passwords, nonces, signatures, ID tokens, `sourceContent`,
    engine stderr at info level, Stripe payloads beyond `event.type`/`id`.
  - The redaction processor (16.2) replaces values of keys matching
    `(?i)(password|secret|token|cookie|signature|authorization|source_content|code)`
    with `[redacted]` in structured log events.
  - Error responses are fixed strings (9.0).

15.5 Authentication hardening

  - bcrypt cost 10 (PRESERVE; raising it invalidates nothing but slows
    sign-in; MAY raise to 12 for NEW hashes and re-hash on successful sign-in).
  - Constant-time dummy compare on sign-in (8.4).
  - Session cookie HttpOnly/SameSite=Lax/Secure(https); 7-day expiry.
  - Wallet nonce single-use, 5-minute expiry, hash-only storage, address
    bound in the signed message; lowercase-only regex.
  - Civic tokens verified by signature/aud/iss/exp; nothing from the body is
    trusted as identity.

15.6 Engine execution

  - argv only; `cwd` is the private temp dir; no shell; no user-controlled
    flags; fixed file names; timeout; output cap; stderr never surfaced.
  - The temp directory is created with `tempfile.mkdtemp` (0700) and the
    file with `O_EXCL|0o600`; removed in `finally`.
  - The engine binary path is configuration, not input.

15.7 Multi-tenancy

  Every Scan/Finding query includes `userId = current user` (or joins to it).
  There is no admin role and no cross-user read path. A missing-or-foreign
  row returns 404, never 403, so ownership is not leaked.

15.8 Dependency hygiene

  Pin every Python dependency with hashes (`pip-compile --generate-hashes`
  or `uv lock`); run `pip-audit` in CI; the repository's own
  `truent deps backend/` (RustSec/OSV matching, lockfile checks) SHOULD run
  in the `supply-chain` workflow against the new directory.

17. DEPLOYMENT AND OPERATIONS
================================================================================

17.1 Artifacts

  - One container image `truent-backend` containing the Python package AND
    the `truent` binary (multi-stage build: `cargo build --release --bin
    truent` in a Rust stage, copy `target/release/truent` to
    `/usr/local/bin/truent` in the Python stage). Both `api` and `worker`
    run from this image with different commands.
  - Dockerfile shape (hardened, matches `truent harden`'s expectations):
      FROM rust:1.82-bookworm@sha256:<digest> AS engine
      WORKDIR /src; COPY . .; RUN cargo build --release --bin truent
      FROM python:3.12-slim-bookworm@sha256:<digest>
      RUN useradd -r -u 10001 truent
      COPY --from=engine /src/target/release/truent /usr/local/bin/truent
      COPY backend /app; WORKDIR /app; RUN pip install --no-cache-dir --require-hashes -r requirements.txt
      USER truent
      ENV TRUENT_BINARY=/usr/local/bin/truent
      CMD ["uvicorn","truent_backend.main:app","--host","0.0.0.0","--port","8000"]
    Worker command override: `python -m truent_backend.worker`.

17.2 Release order

    1. npx prisma migrate deploy      (in web/, only if a Prisma migration was added)
    2. alembic upgrade head           (backend/)
    3. roll out api replicas
    4. roll out worker replicas
    5. roll out the frontend (only needed when 19.3 changes ship)

  Migrations are backward compatible with the previous release (add-only),
  so old and new replicas can overlap.

17.3 Reverse proxy routing

    /api/civic/*   → Next.js   (Civic plugin routes; MUST stay)
    /api/*         → Python API
    /*             → Next.js
  Set `client_max_body_size 4m` (nginx) or the equivalent; forward
  `X-Forwarded-For`/`X-Forwarded-Proto`; strip inbound `X-Request-Id` if you
  do not trust clients to set it.

17.4 Local development

    cd web && docker compose up -d postgres        # or brew services start postgresql@16
    cd web && npx prisma migrate deploy            # creates the tables
    cd backend && cp .env.example .env             # DATABASE_URL, APP_URL=http://localhost:3001, SESSION_SECRET
    cd backend && alembic stamp 0001_baseline
    cd backend && uvicorn truent_backend.main:app --reload --port 8000
    cd backend && python -m truent_backend.worker
    cd web && npm run dev                          # frontend; proxy /api to :8000 via next.config.js rewrites in dev

  Dev proxy: add to `web/next.config.js` `rewrites()` (dev only):
    { source: '/api/:path((?!civic).*)', destination: 'http://localhost:8000/api/:path' }

17.5 Scaling guidance

  - API: CPU-light; 2 replicas × 1 uvicorn worker each is plenty; scale on
    p95 latency.
  - Worker: scale on `truent_scan_queue_depth`; each replica processes one
    scan at a time; a scan is bounded by the 300 s timeout.
  - Postgres: the queue pattern is one row update per claim; no special
    tuning. Add `VACUUM` awareness: `Scan.sourceContent` NULLing creates
    dead tuples; autovacuum defaults are fine at dashboard volumes.

17.6 Runbook entries

  - Queue not draining: check worker logs for `scan_failed` with
    `Analyzer timed out`; check `truent doctor` inside the image; check
    `stale_reclaimed` counts (workers dying mid-scan).
  - Rows stuck in `processing`: the sweep marks them failed after
    10 minutes once `attempts ≥ max`; otherwise they are reclaimed.
  - Engine upgrade: rebuild the image; `/api/catalog` `generated_from`
    shows the new version; run the engine-contract tests (18.4) against the
    new binary before rollout — the JSON contract is versioned by behaviour,
    not by a schema version field.
  - Rotating SESSION_SECRET: invalidates all sessions (users sign in again).
    Do it during low traffic; no other effect.
  - Rotating STRIPE_WEBHOOK_SECRET: update Stripe and the env together;
    events sent in between are retried by Stripe once the secret matches.

20. DECISION LOG
================================================================================

  D1  Postgres as the job queue (SKIP LOCKED), not a broker.
      Preserves the existing worker semantics and keeps one datastore.
  D2  Reuse Prisma tables verbatim; Alembic baseline is a no-op stamp.
      Avoids a data migration and keeps the frontend's client valid during
      the transition.
  D3  HS256 session JWT in an HttpOnly cookie, same 7-day lifetime.
      Verifiable by the Next.js middleware with `jose`; no server-side
      session table needed (NextAuth used stateless JWT too).
  D4  Wallet sign-in stays "address in the email column".
      Changing the identity model is out of scope; it is what the frontend
      and existing rows assume. Flagged as future work (a `walletAddress`
      column on User).
  D5  Civic via ID-token verification, not a session-cookie bridge.
      There is no Python Civic SDK; OIDC verification is the standard
      equivalent of what `getUser()` does. Exact issuer/audience values are
      confirmed at implementation time (8.5).
  D6  Error bodies are fixed strings; first validation message only.
      The frontend displays `error` verbatim; keeping the shape avoids UI
      changes and avoids leaking internals.
  D7  Quotas checked before body validation.
      Matches current ordering exactly; changing it would alter which error a
      user sees in edge cases.
  D8  Worker stores engine error text only for its own typed errors.
      The Node worker could persist arbitrary exception messages into a
      user-visible column; the Python worker does not.
  D9  Card checkout requires a real email (400 instead of Stripe's 500).
      Documented deviation; strictly better UX and no functional loss.
  D10 Crypto route stays fail-closed and non-provisioning.
      Documented gap in the current product; not silently "fixed" here.
  D11 Catalog served live from the binary, cached in-process.
      Removes the build-time `sync-catalog.mjs` step from the release path
      while keeping the guarantee that the site never describes detectors
      the engine lacks.
  D12 No per-user API keys.
      The settings page generates a random string client-side for display;
      no backend route consumes API keys today. Not added.
  D13 Unauthenticated-route rate limits added (Postgres fixed window).
      Not present today; cheap and reduces sign-up/nonce abuse.

APPENDIX D. ATTACK CHAINS (12, engine 0.6.0)
================================================================================

  From `truent exposure … --format json` → `known_chains`. A chain is
  "completed" when at least one detector in every step fires; `break_at` is
  the step index (0-based) where the cheapest fix breaks the chain. Served
  under `/api/catalog` → `attack_chains`.

  session-hijack-cleartext — Session hijack over cleartext
    tactics: Credential Access → Defense Evasion    break_at: 0
    An attacker on the path (public Wi-Fi, a compromised router) waits for the victim to load the site over plain HTTP, which is served without redirecting; the session cookie, lacking Secure, is sent in the clear and replayed.
    step "cleartext reachable": any of rt_no_https_redirect, rt_missing_hsts
    step "cookie leaks": any of rt_insecure_cookie, gen_web_insecure_cookie

  credential-file-exposure — Credentials served to the internet
    tactics: Reconnaissance → Credential Access → Initial Access    break_at: 0
    A configuration or repository file is fetched anonymously from the web root; it contains credentials that the attacker uses directly against the database, cloud account or third-party API.
    step "file exposed": any of rt_exposed_sensitive_path
    step "credentials in files": any of gen_hardcoded_secret, gen_private_key_committed

  injection-to-data-exfiltration — Injection reaching a reachable database
    tactics: Initial Access → Collection → Exfiltration    break_at: 0
    Untrusted input reaches a query; the database it runs against is publicly addressable or unencrypted, so the injection turns into bulk read of the store rather than a single-row leak.
    step "injection": any of gen_sql_injection
    step "data store exposed": any of gen_iac_public_database, gen_iac_unencrypted_storage

  ci-takeover-to-supply-chain — CI takeover becomes a supply-chain compromise
    tactics: Initial Access → Credential Access → Persistence → Impact    break_at: 0
    A pull request from a fork runs with repository secrets (pwn request / script injection); the attacker exfiltrates the publishing token, or edits an unpinned action, and ships a poisoned release to every downstream user.
    step "CI code execution": any of gen_ci_pwn_request, gen_ci_script_injection
    step "secrets or publish path in reach": any of gen_ci_secret_exposed, gen_ci_unpinned_action, gen_hardcoded_secret

  xss-to-account-takeover — Stored/reflected XSS to account takeover
    tactics: Execution → Credential Access    break_at: 0
    Script injected through an HTML sink runs in the victim's browser unrestricted by a CSP; the session cookie is readable by script (no HttpOnly) and is sent to the attacker.
    step "script injection": any of gen_xss_sink
    step "no CSP": any of rt_missing_csp
    step "cookie readable": any of rt_insecure_cookie, gen_web_insecure_cookie

--- scripts/scan-worker.mjs -----------------------------------------------------
  import { PrismaClient } from '@prisma/client'
  import { PrismaPg } from '@prisma/adapter-pg'
  import { randomUUID } from 'node:crypto'
  import { execFile } from 'node:child_process'
  import { mkdtemp, rm, writeFile } from 'node:fs/promises'
  import { tmpdir } from 'node:os'
  import path from 'node:path'
  import { promisify } from 'node:util'
  import { chainFor, fileNameFor, mapFinding } from '../lib/scan-worker-core.mjs'
  
  const execFileAsync = promisify(execFile)
  const databaseUrl = process.env.DATABASE_URL
  if (!databaseUrl) throw new Error('DATABASE_URL is required')
  
  const prisma = new PrismaClient({ adapter: new PrismaPg({ connectionString: databaseUrl }) })
  const workerId = process.env.HOSTNAME || `worker-${randomUUID()}`
  const pollMs = Math.max(Number(process.env.SCAN_WORKER_POLL_MS || 1000), 100)
  const maxAttempts = Math.max(Number(process.env.SCAN_MAX_ATTEMPTS || 3), 1)
  const binary = process.env.TRUENT_BINARY || 'truent'
  let stopping = false
  
  async function claim() {
    await prisma.$executeRaw`
      UPDATE "Scan"
      SET "status" = 'failed', "error" = 'Worker stopped before completing the scan',
          "completedAt" = NOW(), "sourceContent" = NULL, "updatedAt" = NOW()
      WHERE "status" = 'processing' AND "attempts" >= ${maxAttempts}
        AND "claimedAt" < NOW() - INTERVAL '10 minutes'
    `
    const rows = await prisma.$queryRaw`
      UPDATE "Scan"
      SET "status" = 'processing', "claimedAt" = NOW(), "workerId" = ${workerId},
          "attempts" = "attempts" + 1, "updatedAt" = NOW()
      WHERE "id" = (
        SELECT "id" FROM "Scan"
        WHERE "attempts" < ${maxAttempts}
          AND ("status" = 'queued'
           OR ("status" = 'processing' AND "claimedAt" < NOW() - INTERVAL '10 minutes'))
        ORDER BY "createdAt" ASC
        FOR UPDATE SKIP LOCKED LIMIT 1
      )
      RETURNING *
    `
    return rows[0] || null
  }
  
  async function run(scan) {
    const chain = chainFor(scan.language)
    const fileName = fileNameFor(scan.language)
    if (!chain || !fileName || !scan.sourceContent) throw new Error('Scan source or language is invalid')
  
    const work = await mkdtemp(path.join(tmpdir(), 'truent-scan-'))
    // Detectors classify by file name (Dockerfile, *.tf, *.py …), so the
    // submission is written under the name its language expects.
    const source = path.join(work, fileName)
    const started = Date.now()
    try {
      await writeFile(source, scan.sourceContent, { mode: 0o600 })
      let stdout
      try {
        // Run from the scratch directory and pass the bare file name, so the
        // engine reports `app.py:7`, not a temp path the user never sees.
        ;({ stdout } = await execFileAsync(
          binary,
          ['scan', fileName, '--chain', chain, '--output', 'json', '--no-color'],
          { cwd: work, timeout: 5 * 60_000, maxBuffer: 20 * 1024 * 1024, env: { ...process.env, NO_COLOR: '1' } },
        ))
      } catch (error) {
        // The CLI intentionally exits non-zero when a proven finding crosses its
        // gate. That is a valid report, not a worker failure.
        if (!error.stdout) throw error
        stdout = error.stdout
      }
      const report = JSON.parse(stdout)
      if (!Array.isArray(report.violations)) throw new Error('Analyzer returned an invalid report')
      const findings = report.violations.map((finding) => mapFinding(scan.id, finding))
      await prisma.$transaction([
        prisma.finding.deleteMany({ where: { scanId: scan.id } }),
        ...findings.map((data) => prisma.finding.create({ data })),
        prisma.scan.update({
          where: { id: scan.id },
          data: {
            status: 'complete', completedAt: new Date(), durationMs: Date.now() - started,
            error: null, sourceContent: null,
          },
        }),
      ])
    } finally {
      await rm(work, { recursive: true, force: true })
    }
  }
  
  async function fail(scan, error) {
    const retry = scan.attempts < maxAttempts
    await prisma.scan.update({
      where: { id: scan.id },
      data: {
        status: retry ? 'queued' : 'failed',
        error: error instanceof Error ? error.message.slice(0, 1000) : 'Analyzer failed',
        claimedAt: null, workerId: null,
        ...(!retry ? { completedAt: new Date(), sourceContent: null } : {}),
      },
    })
  }
  
  async function main() {
    while (!stopping) {
      const scan = await claim()
      if (!scan) {
        if (process.argv.includes('--once')) break
        await new Promise((resolve) => setTimeout(resolve, pollMs))
        continue
      }
      try { await run(scan) } catch (error) { console.error(`Scan ${scan.id} failed`, error); await fail(scan, error) }
      if (process.argv.includes('--once')) break
    }
  }
  
  for (const signal of ['SIGTERM', 'SIGINT']) process.on(signal, () => { stopping = true })
  main().catch((error) => { console.error('Worker crashed', error); process.exitCode = 1 }).finally(() => prisma.$disconnect())

  // Keep in sync with lib/engine.ts LANGUAGES (the worker cannot import TS).
  const LANGUAGES = {
    solidity: { chain: 'evm', file: 'contract.sol' },
    rust: { chain: 'solana', file: 'program.rs' },
    soroban: { chain: 'soroban', file: 'contract.rs' },

    python: { chain: 'general', file: 'app.py' },
    javascript: { chain: 'general', file: 'app.js' },
    typescript: { chain: 'general', file: 'app.ts' },
    go: { chain: 'general', file: 'main.go' },
    shell: { chain: 'general', file: 'script.sh' },
    dockerfile: { chain: 'general', file: 'Dockerfile' },
    terraform: { chain: 'general', file: 'main.tf' },
    yaml: { chain: 'general', file: 'deployment.yaml' },
  }
  
  export const SUPPORTED_LANGUAGES = Object.keys(LANGUAGES)
  export const chainFor = (language) => LANGUAGES[language]?.chain
  /** The file name the source is written to; detectors classify by name. */
  export const fileNameFor = (language) => LANGUAGES[language]?.file
  /** Kept for callers that only want the extension. */
  export const extensionFor = (language) => {
    const f = fileNameFor(language)
    if (!f) return undefined
    const i = f.lastIndexOf('.')
    return i === -1 ? '' : f.slice(i)
  }
  
  const SEVERITIES = new Set(['critical', 'high', 'medium', 'low', 'info'])
  const EXPLOITABILITY = new Set(['likely', 'possible', 'unlikely', 'theoretical'])
  
  /**
   * Map one `violations[]` entry of `truent scan --output json` to a durable
   * Finding row. The engine emits `file`/`line` separately from the display
   * `location`, its `recommendation` is the exposure table's fix, and
   * `evidence` is the honesty contract ("lead" | "proven").
   */
  export function mapFinding(scanId, finding) {
    const rawSeverity = String(finding.severity || 'low').toLowerCase()
    const severity = SEVERITIES.has(rawSeverity) ? rawSeverity : 'low'
    const invariantId = typeof finding.invariant_id === 'string' && finding.invariant_id ? finding.invariant_id : null
    const title = finding.title || (invariantId ? invariantId.replaceAll('_', ' ') : 'security finding')
    const description = String(finding.message || 'Security issue detected')
  
    // Older engine output carried only `location: "file:line"`.
    let file = typeof finding.file === 'string' && finding.file ? finding.file : null
    let line = Number.isInteger(finding.line) && finding.line > 0 ? finding.line : null
    if (!file && typeof finding.location === 'string') {
      const m = finding.location.match(/^(.*):(\d+)$/)
      if (m) { file = m[1]; line = Number(m[2]) || null } else file = finding.location || null
    }
    const location = file ? `${file}${line ? ` · Line ${line}` : ''}` : null
  
    const evidence = finding.evidence === 'proven' ? 'proven' : 'lead'
    const exploitability = EXPLOITABILITY.has(finding.exploitability) ? finding.exploitability : null
    const fix = typeof finding.fix === 'string' && finding.fix ? finding.fix : null
    const verify = typeof finding.verify === 'string' && finding.verify ? finding.verify : null
    const recommendation = fix || finding.recommendation || 'Review this finding and apply the relevant invariant guidance.'
    const reasons = Array.isArray(finding.exploit_reasons) ? finding.exploit_reasons.filter((r) => typeof r === 'string') : []
    const impact = reasons.length
      ? `${evidence === 'proven' ? 'Proven. ' : ''}${reasons.join('; ')}`
      : evidence === 'proven' ? 'Proven: observed on the wire or produced by a solver.' : null
  
    const fingerprint = createHash('sha256')
      .update(`${severity}\0${invariantId || title}\0${file || ''}\0${line || ''}`)
      .digest('hex')
  
    return {
      scanId, severity, title, description, location, line, impact, recommendation, fingerprint,
      invariantId,
      chain: typeof finding.chain === 'string' ? finding.chain : null,
      evidence, exploitability, fix, verify,
      cwe: typeof finding.cwe === 'string' && finding.cwe ? finding.cwe : null,
      snippet: typeof finding.code_snippet === 'string' && finding.code_snippet ? finding.code_snippet.slice(0, 2000) : null,
    }
  }

  import { type NextAuthOptions } from 'next-auth'
  import CredentialsProvider from 'next-auth/providers/credentials'
  import { PrismaAdapter } from '@next-auth/prisma-adapter'
  import { getUser as getCivicUser } from '@civic/auth/nextjs'
  import prisma from '@/lib/prisma'
  import { CIVIC_ENABLED } from '@/lib/civic'
  import { resolveCivicUser } from '@/lib/civic-user'
  import bcrypt from 'bcrypt'
  import { ethers } from 'ethers'
  import { createHash } from 'crypto'
  
  // A precomputed hash with no matching password, compared against when a user
  // isn't found so that bcrypt.compare() always runs and takes roughly the same
  // time either way. Without this, an unknown email short-circuits before the
  // (comparatively slow) bcrypt.compare call, letting an attacker distinguish
  // "wrong password" from "no such account" by response time (email enumeration).
  const DUMMY_PASSWORD_HASH = bcrypt.hashSync('truent-timing-safety-dummy', 10)
  
  /**
   * Verify wallet signature for Web3 authentication
   */
  async function verifyWalletSignature(
    address: string,
    message: string,
    signature: string
  ): Promise<boolean> {
    try {
      const normalizedAddress = address.toLowerCase()
      const match = message.match(/^Truent sign-in\nAddress: (0x[a-f0-9]{40})\nNonce: ([a-f0-9]{48})$/)
      if (!match || match[1] !== normalizedAddress) return false
      const challenge = await prisma.authNonce.findUnique({ where: { address: normalizedAddress } })
      if (
        !challenge ||
        challenge.expiresAt <= new Date() ||
        challenge.nonceHash !== createHash('sha256').update(match[2]).digest('hex')
      ) return false
      const recoveredAddress = ethers.verifyMessage(message, signature)
      if (recoveredAddress.toLowerCase() !== normalizedAddress) return false
      await prisma.authNonce.delete({ where: { address: normalizedAddress } })
      return true
    } catch (error) {
      console.error('Wallet signature verification error:', error)
      return false
    }
  }

            })
          }
  
          return {
            id: user.id,
            email: user.email,
            name: user.name,
            image: user.image,
          }
        },
      }),
    ],
    callbacks: {

--- lib/civic-user.ts -----------------------------------------------------------
  import type { User as CivicUser } from '@civic/auth'
  import prisma from '@/lib/prisma'
  
  export type LinkedUser = { id: string; email: string | null; name: string | null; image: string | null }
  
  /**
   * Map a verified Civic identity onto an application user.
   *
   * Order of resolution:
   *   1. a user already linked to this Civic id;
   *   2. an existing account with the same (verified) email — linked on first use
   *      so someone who signed up with a password keeps their scans and plan;
   *   3. a new account.
   *
   * The caller must only pass a user obtained from Civic's server-side session
   * (`getUser()` from `@civic/auth/nextjs`), never from the request body.
   */
  export async function resolveCivicUser(civic: CivicUser): Promise<LinkedUser> {
    const select = { id: true, email: true, name: true, image: true }
    const email = civic.email?.trim().toLowerCase() || null
    const name = civic.name || civic.username || (email ? email.split('@')[0] : `Civic ${civic.id.slice(0, 6)}`)
  
    const linked = await prisma.user.findUnique({ where: { civicId: civic.id }, select })
    if (linked) return linked
  
    if (email) {
      const byEmail = await prisma.user.findUnique({ where: { email }, select })
      if (byEmail) {
        return prisma.user.update({
          where: { id: byEmail.id },
          data: { civicId: civic.id, emailVerified: new Date(), image: byEmail.image ?? civic.picture ?? null },
          select,
        })
      }
    }
  
    return prisma.user.create({
      data: {
        civicId: civic.id,
        email,
        emailVerified: email ? new Date() : null,
        name,
        image: civic.picture ?? null,
      },
      select,
    })
  }

  import { z } from 'zod'
  import prisma from '@/lib/prisma'

  const submissionSchema = z.object({
    code: z.string().min(1, 'Code is required').max(500_000, 'Code exceeds maximum size'),
    language: z.enum(['solidity', 'rust', 'move', 'soroban', 'python', 'javascript', 'typescript', 'go', 'shell', 'dockerfile', 'terraform', 'yaml']).default('solidity'),
    projectName: z.string().trim().min(1).max(120).optional(),
  })
  
  export async function POST(request: NextRequest) {
    try {
      const user = await getCurrentUser()
      if (!user) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })
  
      const minuteAgo = new Date(Date.now() - 60_000)
      if (await prisma.scan.count({ where: { userId: user.id, createdAt: { gte: minuteAgo } } }) >= 5) {
        return NextResponse.json(
          { error: 'Rate limit exceeded. Please wait before submitting another scan.' },
          { status: 429, headers: { 'Retry-After': '60' } },
        )
      }
  
      const monthStart = new Date()
      monthStart.setUTCDate(1)
      monthStart.setUTCHours(0, 0, 0, 0)
      const activePlan = user.subscription?.status === 'active' ? user.subscription.plan : null
      const used = await prisma.scan.count({ where: { userId: user.id, createdAt: { gte: monthStart } } })

        data: {
          userId: user.id,
          projectName: input.projectName || 'Untitled scan',

          status: 'queued',

      })

  import { NextRequest, NextResponse } from 'next/server'

  import prisma from '@/lib/prisma'
  import { isPlanId } from '@/lib/plans'

  function stripeClient() {
    if (!process.env.STRIPE_SECRET_KEY) throw new Error('STRIPE_SECRET_KEY is not configured')
    return new Stripe(process.env.STRIPE_SECRET_KEY)
  }
  
  export async function POST(request: NextRequest) {
    const signature = request.headers.get('stripe-signature')
    const secret = process.env.STRIPE_WEBHOOK_SECRET
    if (!signature || !secret) {
      return NextResponse.json({ error: 'Webhook is not configured' }, { status: 503 })
    }
  
    let event: Stripe.Event
    try {
      const stripe = stripeClient()
      event = stripe.webhooks.constructEvent(await request.text(), signature, secret)
    } catch (error) {
      console.error('Invalid Stripe webhook', error)
      return NextResponse.json({ error: 'Invalid signature' }, { status: 400 })
    }
  
    if (event.type === 'checkout.session.completed') {
      const checkout = event.data.object
      const userId = checkout.metadata?.userId
      const plan = checkout.metadata?.planId
      if (userId && plan && isPlanId(plan) && checkout.subscription) {
        await prisma.subscription.upsert({
          where: { userId },
          create: {
            userId,
            provider: 'stripe',
            providerCustomerId: String(checkout.customer || ''),
            providerSubscriptionId: String(checkout.subscription),
            plan,
            status: 'active',
          },
          update: {
            providerCustomerId: String(checkout.customer || ''),
            providerSubscriptionId: String(checkout.subscription),
            plan,
            status: 'active',
          },
        })
      }
    }
  
    if (event.type === 'customer.subscription.updated' || event.type === 'customer.subscription.deleted') {
      const subscription = event.data.object
      await prisma.subscription.updateMany({
        where: { providerSubscriptionId: subscription.id },
        data: {
          status: subscription.status,
          cancelAtPeriodEnd: subscription.cancel_at_period_end,
          currentPeriodEnd: new Date(subscription.items.data[0]?.current_period_end * 1000),
        },
      })
    }
  
    return NextResponse.json({ received: true })
  }

  /**
   * Verify a crypto payment transaction on-chain.
   *
   * Fails closed: if the RPC endpoint or receiver address isn't configured, this
   * returns false rather than approving the payment. A payment gate must never
   * default to "approved" when unconfigured.
   */
  async function verifyBlockchainTransaction(
    transactionHash: string,
    walletAddress: string
  ): Promise<boolean> {
    const rpcUrl = process.env.ETHEREUM_RPC_URL
    const receiverAddress = process.env.PAYMENT_RECEIVER_ADDRESS
  
    if (!rpcUrl || !receiverAddress) {
      console.error(
        'Crypto payment verification is not configured (ETHEREUM_RPC_URL / PAYMENT_RECEIVER_ADDRESS missing)'
      )
      return false
    }
  
    if (!/^0x([A-Fa-f0-9]{64})$/.test(transactionHash)) {
      return false
    }
  
    try {
      const provider = new ethers.JsonRpcProvider(rpcUrl)
      const receipt = await provider.getTransactionReceipt(transactionHash)
  
      if (!receipt || receipt.status !== 1) {
        return false
      }
  
      if (receipt.to?.toLowerCase() !== receiverAddress.toLowerCase()) {
        return false
      }
  
      const tx = await provider.getTransaction(transactionHash)
      if (!tx || tx.from.toLowerCase() !== walletAddress.toLowerCase()) {
        return false
      }
  
      // NOTE: this confirms the transaction succeeded and moved funds between the
      // claimed wallet and receiver address, but does not yet verify the paid
      // amount/token matches the invoice (ERC-20 token transfers require decoding
      // the Transfer event log, not just the native tx value). Until that's added,
      // treat this as "a real transaction between these two addresses happened",
      // not "the correct amount was paid".
      const confirmations = await receipt.confirmations()
      return confirmations >= 1
    } catch (error) {
      console.error('Blockchain verification error:', error)
      return false
    }
  }

APPENDIX G. GLOSSARY
================================================================================

  Analyzer / engine   One of the chain-specific static analyzers (EVM, Solana,
                      Move, Soroban) or the general repository analyzer inside
                      the `truent` binary. "Chain" in engine JSON names the
                      analyzer, not a network.
  Attack chain        A named composition of findings that together form a
                      known attack path (Appendix D).
  Catalog             The engine-derived metadata object (detectors, pathways,
                      attack chains) the frontend uses for its library, docs
                      and counts.
  Claim               The atomic `UPDATE … FOR UPDATE SKIP LOCKED` that moves a
                      Scan from queued to processing for one worker.
  Civic               Civic Auth: OAuth/passkey/embedded-wallet identity
                      provider; its Next.js routes stay under `/api/civic`.
  cuid                Prisma's collision-resistant id format used by existing
                      rows; the backend generates cuid2 ids.
  Detector            One rule in the engine with an `invariant_id`, a taxonomy
                      row and an exposure profile (fix, verify, attack profile).
  Evidence            The honesty contract on every finding: `lead` (static
                      inference) or `proven` (observed/solver-produced).
  Exploitability      likely / possible / unlikely / theoretical, computed by
                      the engine from the detector's attack profile + evidence.
  Fingerprint         sha256(severity, invariant id or title, file, line);
                      unique per scan; dedupe key.
  Finding             A stored engine violation, owned by a Scan, with a user
                      triage `status` (open / acknowledged / resolved).
  General analyzer    The repository analyzer for Python, JS/TS, Go, shell,
                      Dockerfiles, Kubernetes/compose, Terraform, CloudFormation,
                      GitHub Actions, secrets.
  Lead                See Evidence.
  Nonce (wallet)      A 48-hex-char challenge embedded in the sign-in message,
                      stored hashed, single-use, 5-minute expiry.
  Pathway             One of 21 security disciplines and how the engine covers
                      it (native / hosted / assess).
  Plan                A billing tier; only `professional` exists (10,000 scans
                      per month); free tier is 5.
  Proven              See Evidence. Only `probe` and `symbolic` produce it.
  Scan                A user submission of one source file in one language,
                      with a lifecycle queued → processing → complete | failed.
  Session             The backend-issued HS256 JWT in the `truent_session`
                      cookie (7 days).
  SKIP LOCKED         PostgreSQL row-lock option that lets many workers pick
                      different rows without blocking.
  Stale reclaim       Re-queuing (or failing) `processing` rows whose worker
                      has not finished within 10 minutes.
  Taxonomy            The engine's mapping of every detector to CWE, SWC, OWASP
                      SC Top 10, DASP, MITRE ATT&CK and NIST CSF 2.0.
  Worker              The Python process that runs the engine on queued scans.
